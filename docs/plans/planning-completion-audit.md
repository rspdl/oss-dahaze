## 실제 API 첫 연결

사용자의 기존 키 재사용 승인 후 원래 env 파일을 읽기만 하고, 키를 복사하거나 출력하지 않았다.
기존 모델 설정 `gpt-4.1`은 custom grammar 요청을 HTTP 400으로 거절했다.
검수 프로세스에서만 저장소 기본 모델 `gpt-5-nano`를 사용한 요청은 약 40초에 성공했다.
생성된 최소 예약 명세를 별도 planning compiler로 검사한 결과 오류 0건과
`RSPDL-DATA-W001` 경고 1건이었다. 이는 단일 생성·컴파일 연결의 증거이며 프로젝트
인터뷰·작업 복구·진단 해결 반복 전체가 완성됐다는 증거는 아니다.

## 실제 AI 통합 검수 중간 결과

검수 프로세스의 모델만 gpt-5-mini로 지정했다. 기존 사용자 설정 파일은 수정하지 않았다.
Planning 문법 예제의 실제 생성은 16초에 완료됐고 compiler 진단 0건으로, 업무·조회 결과·행동
결과를 유지했다. 동일한 복잡한 예제의 gpt-5-nano 생성은 오류가 남았으며 컴파일 게이트가 잡았다.

별도 DB·API·worker에서 실제 인터뷰 작업을 요청했다. 같은 요청을 반복해도 작업 하나와 사용자
메시지 하나만 생겼다. strict JSON schema 결함과 worker의 DB 속성 로딩 결함을 발견해 수정한
뒤 실제 인터뷰 응답·질문·미정 제안 저장에 성공했다. 브라우저의 채택/이유 포함 보류는 200으로
처리되고 새로고침 후 판단 두 건이 유지됐다. 단, 채택 시 원래 정책 내용이 이유로 덮이는 결함을
발견해 수정 대상으로 남겼다. 이 시점은 전체 AI 루프 완료 판정이 아니다.


## 영속 작업과 최종 하네스 중간 검수 (cafab42)

주 에이전트가 별도 DB에서 `./scripts/check.sh` 전체를 실행해 통과했다. API 214개, 웹 201개,
에디터 46개 테스트와 플랫폼·계층 경계·린트·타입·마이그레이션 일치·OpenAPI 드리프트·codegen·
프로덕션 빌드가 통과했다. API의 3개 skip은 별도 native/전용 DB 검수와 구분한다.

독립 PostgreSQL 검수에서는 요청 중복·다른 payload 충돌·동시 재시도·오래된 초안·취소된 lease
회수·오래된 worker 쓰기 차단·동결 맥락 보존·프로젝트 접근 제한 8개가 통과했다. 별도 worker
검수 5개는 두 문서 중 첫 문서의 정확한 checkpoint 재사용, 실행 중 취소, 회수 후 이전 worker
차단, 3회 수정 후 오류 초안 보관, 중복 문서 계획 거부를 확인했다.

실제 UI에서 실패 작업의 재시도를 눌러 이전 작업에 연결된 새 작업이 생성되고, 새로고침 후에도
계속 조회되는 것을 확인했다. 채택 정책 원문과 사람 판단 이유 분리도 실제 응답으로 확인했다.

다만 실서비스 연결의 새 문서 생성은 아직 통과 처리하지 않았다. 문법 제약 생성의 시간 초과와
중복 계획을 발견했고 유한한 계획 형식 수정·진행 상태·시간 한도를 보완했다. 대조 실험에서
JSON으로 받은 문서는 5.8초/진단 0건이었지만 요청한 흐름과 업무 계약이 빠져 있어 반려했다.
컴파일 오류 0건만으로 사용자의 요구 충족을 대신하지 않는다. 새 문법 전용 저작 지침을 분리한
뒤 실제 생성과 적용을 다시 확인해야 한다.


## 실제 AI 연속 시나리오 최종 검수

격리된 review DB와 로컬 planning compiler에서 기존 키를 읽기만 하고 gpt-5.4-mini를 사용했다.
기존 사용자 env는 바꾸지 않았다. 앱 기본 모델·예시 설정은 실제 검수한 모델로 맞췄다.

1. 첫 새 생성 `359ad62e`는 약 53초/진단 0건이었지만 요청하지 않은 연락처 조회를 만들었으므로
   반려했다. standalone planning 지침과 수동 획득 예제를 보완했다. 독립 검수에서 발견한 예제의
   요청 범위 불일치, 정적 분석과 실제 실행 구분, 지원 밖 정책 보존 규칙도 수정했다.
2. 다음 새 생성 `233eca0b`는 중복 ID `RSPDL-LINK-003`와 중복 조작 `RSPDL-DATA-004`를 담은
   초안 `9aa9e8dc`를 반환했다. 유한한 수정 후에도 남은 오류는 보관되며 저장 명세를 바꾸지 않았다.
3. 브라우저에서 이 후보를 선택해 인터뷰 `3732b0a8`로 의도를 명확히 했다. 불필요한 조회를 제거하고
   수동 입력만 사용한다는 제안 `2893c753`을 채택했다. 정책 본문과 사람의 판단 이유가 따로 남았다.
4. 선택 후보와 진단을 입력받은 생성 `ce733b15`가 약 13초에 초안 `a618e2d2`를 만들었다.
   진단 0건, 정보구조·2화면·2결과·성공 이동/실패 메시지·retry·수동 획득·완료 필수 연락처가
   남았으며, 불필요한 lookup과 기존 모델 행동 입력은 사라졌다. 실제 UI 명시적 적용은 HTTP 200,
   `applied: true`, 프로젝트 버전 1이었다.
5. 실제 화면 체험에서 viewport 390×844, 연락처 입력, 실패 메시지가 같은 화면 안에 표시됨,
   같은 버튼으로 성공 결과 재시도 후 완료 화면 이동, 다시 입력 화면 선택 시 값 보존을 확인했다.
6. 최종 소스에서 `업무.획득`만 제거한 반례 `15f347ee`는 compiler의 `RSPDL-WORKFLOW-001`과
   누락 경로를 반환했다. 적용 시도는 HTTP 200/`applied: false`였고 기존 버전·원문 hash는 불변이었다.
7. 실제 UI로 개발 전달 스냅샷 3을 만들었다. 프로젝트 버전 1, 원문 hash `5bfd722a5535…`, 명세 원문,
   채택 결정 2개, IA·읽기 전용 화면·기능명세·업무 획득 연결이 같은 전달본에 표시됐다.

취소 검수 `efc7a036`는 `cancelled`/결과 없음으로 끝났다. 기본 모델의 일회 생성이 항상 성공한다고
주장하지 않는다. 검수한 제품 흐름은 오류·의도 차이를 드러내고 인터뷰와 명시적 판단으로 수정하는
과정이다. 컴파일 통과는 실제 입력값이나 외부 결제 실행의 증명이 아니다.

정식 compiler 릴리스·저장 문서 승격 검사·핀 갱신·운영 배포는 아직 수행하지 않았다.
