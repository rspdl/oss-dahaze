# dahaze — 인터뷰에서 검증된 기획과 개발 전달까지

2026-09-23 · 인터뷰 합의에 따른 구현 계획 · 실행 진행 중

실제 구현·검수 현황은 [구현 기록](implementation-status.md)에서 관리한다. 아래의 조사 기준과
실행 전 평가는 계획 작성 시점을 나타내며 구현 완료를 뜻하지 않는다.

## 1. 목적과 완료 기준

기획자가 아이디어에서 출발해 AI와 인터뷰하면서 업무 규칙을 명확히 하고, 기능명세·데이터 모델·IA·와이어프레임을 같은 의도로 유지한다. 누락과 충돌은 RSPDL 컴파일러가 판정하고, AI는 설명·질문·수정안을 제공한다. 개발자는 프로젝트 전체의 특정 버전을 화면·요소·기능·데이터·정책 사이를 탐색하며 읽는다.

대표 규모는 화면 30~100개와 사용 환경 2~4개다. 초기 사용자는 단독 기획자이며 실시간 공동 편집은 제외한다. 첫 통합 검증 사례는 항공편 선택→승객 정보→결제→예약 완료와 결제 실패·재시도다. 항공업 규정을 재현하는 것이 아니라 가상 정책을 명시한 시험 프로젝트로 사용한다.

제품 작업 반복은 인터뷰→작성·컴파일→결과 검토→추가 인터뷰다. 첫 작성 전에 목적·범위·핵심 업무 규칙을 정한다. 인터뷰 중 매 답변마다 IA를 바꾸지 않고, 작성 결과에서 명세와 IA를 함께 제시한다.

## 2. 확정된 제품 결정

- AI 대화 중심이며 직접 시각 편집도 지원한다. AI의 추천 정책은 사용자가 채택하기 전까지 미정이다.
- 검토 첫 화면은 정리된 목적·정책, 미정 결정, 컴파일러 진단, AI 확인 질문, 검증 미지원 범위를 구분한다. 임의의 완성도 점수를 만들지 않는다.
- AI는 영향이 큰 문제부터 추천한다. 사용자는 다른 문제를 선택하거나 보류할 수 있다. 보류 이유와 관련 항목을 남겨 이후 작업에서 다시 제시한다.
- 초안은 컴파일 결과·변경 요약을 본 뒤 사람이 적용한다. 오류가 남아도 작업 초안은 보존하지만 확정 명세와 구분한다.
- 와이어프레임은 준비된 기능부터 생성할 수 있다. 미정 요소를 놓아볼 수 있지만 미정 동작을 실행하지 않는다.
- 회색 기반 화면, 로고·이미지 자리표시자, 풍부한 샘플 데이터. 정상·빈 목록·긴 문구·많은 데이터 상황을 제공한다.
- 요소 추가·삭제·순서·배치·크기와 연결을 편집한다. 디자인 수치는 바로 저장·실행 취소할 수 있다. 기능 의미 변경은 RSPDL 초안·컴파일·검토를 거친다.
- 고객 모바일·운영자 PC 등 사용 환경을 먼저 정의한다. 환경별 기능·화면 수·흐름이 달라도 공통 데이터와 정책은 공유한다. 서로 다른 역할의 체험 상태를 실시간 연결하지 않는다.
- 기존 배치는 AI 수정 뒤에도 보존한다. 새 요소만 기본 배치를 제안하고 큰 재구성은 별도 변경안으로 제시한다.
- 입력·클릭과 성공·실패·로딩 상황 선택을 지원한다. 정책을 전부 실행하는 시뮬레이터는 후속이다.
- 화면에서 기능명세를, 버튼에서 행동·조건·결과를, 입력/표시 요소에서 필드·필수 조건·값의 출처를 확인한다.
- 프로젝트 전체 버전을 읽기 전용 화면·다운로드·MCP로 전달한다. 부분 전달, 의존성별 전달 제외, 복잡한 준비 완료 판정은 만들지 않는다. 미정·진단·미지원은 전달본에도 표시한다.
- 적용한 변경 묶음 단위로 명세와 디자인 상태를 복원한다. 전달 버전 간 변경 비교를 제공한다.

## 3. 확인한 현재 상태

원격 기준: dahaze origin/main 33cff11, origin/develop c184198. RSPDL origin/main 3c8fa81(0.1.3). fetch만 수행했으며 로컬 dahaze main은 원격보다 17커밋 뒤에 있다. 아래 평가는 원격 소스와 로컬 RSPDL 소스 열람에 근거하며 실행 검증 결과가 아니다.

| 영역 | 현재 기반 | 필요한 변화 |
|---|---|---|
| 컴파일러 연동 | dahaze 원격은 rspdl 0.1.2 고정 | format SDK가 있는 0.1.3 평가 및 이후 의미 확장 릴리스 승격 |
| IA·흐름 | React Flow 읽기 전용 보드와 목업 | 직접 편집, 진단 연결, 환경별 탐색, 프로토타입 |
| 목업 | 닫힌 레이아웃 어휘, PC 1024/모바일 390 폭 | 사용자 지정 화면 크기·높이, 데이터 표시, 실제 입력과 상태 |
| AI 저작 | 단일 문서 초안→컴파일→최대 3회 수리 | 프로젝트 인터뷰, 지속 대화, 결정·보류, 여러 문서 변경안 |
| AI 대화 UI | 화면 로컬 이력; revise API에 대화 이력을 보내지 않음 | 서버 보관 및 실제 맥락 전달, 관련 결정 검색 |
| 저장 | 문서별 리비전, 컴파일 캐시 | 프로젝트 변경 묶음, 오류 초안 보관, 전체 스냅샷·복원 |
| 데이터 모델·MCP | 데이터 모델 뷰와 기존 MCP 유스케이스 | 같은 전달 버전에 고정된 탐색·다운로드·MCP |

여러 파일을 compile 요청으로 묶을 수 있다는 사실만으로 모든 파일 간 의미 참조와 경로 검증을 보장할 수 없다. 현재 compiler는 파일별 분석 뒤 중복 모듈·심볼 등 workspace 검사를 수행한다. 공통 모델을 별도 문서에서 참조하는 사례는 0단계에서 명시적으로 검증하고, 부족하면 compiler linking 계약으로 해결한다. dahaze가 별도 이름 해석기를 만들지 않는다.

## 4. Manyfast에서 가져올 경험과 dahaze에 맞게 바꿀 부분

- 기능명세의 계층적 탐색과 조건·동작·결과·예외·권한·데이터 검토 구조를 참고한다. 이 구조의 이름을 그대로 독립 DB 정책 사본으로 만들지는 않는다.
- IA 트리, 흐름 캔버스, 페이지별 생성·재생성, 편집과 체험 모드 분리를 참고한다.
- 생성 진행과 실패 페이지를 표시하고 완료된 페이지부터 검토한다. 재시도는 완료된 페이지를 덮어쓰지 않는다.
- 화면 명세는 RSPDL에서 얻는다. 시각 편집도 의미 변경이면 원문 변경안이 된다. 별도 화면 데이터가 두 번째 기능 명세가 되지 않는다.
- 화면·명세의 의미상 불일치는 컴파일러 진단이다. 오래된 결과 표시나 원문 버전 충돌은 dahaze의 상태 표시로 분리한다.

참고: [와이어프레임](https://docs.manyfast.io/plan/wireframe), [기능명세서](https://docs.manyfast.io/plan/features), [IA](https://docs.manyfast.io/plan/ia), [유저 플로우](https://docs.manyfast.io/plan/user-flow).

## 5. 데이터와 기술 경계

기존 Next.js·React·TypeScript, React Flow, FastAPI, PostgreSQL, TanStack Query, zustand, CodeMirror를 유지한다. 새 그래프 엔진이나 자유 디자인 도구를 도입할 근거는 없다. 자동 배치는 기존 구현을 먼저 측정하고 복잡한 연결에서 부족할 때만 추가 라이브러리를 비교한다.

| 소유자 | 소유하는 정보 |
|---|---|
| RSPDL 원문과 컴파일러 | 모델·필드·정책·행동·의미 있는 화면 구조·경로, 확장될 조건/결과/업무 계약과 진단 |
| dahaze | 대화·결정 근거·미정 제안, 디자인 좌표·크기, 화면 크기 설정, 샘플 데이터, 작업 이력·전달 스냅샷 |
| 파생 뷰/캐시 | 읽기 좋은 기능명세, IA, ERD, 와이어프레임, 연결 탐색, 컴파일 결과 |

기능명세의 검증 가능한 문장은 RSPDL 원문으로 연결한다. 목적·설명·결정 이유 등 자유 서술은 사용자 작성 맥락으로 보관할 수 있지만, 실행 규칙을 그 서술만으로 판정하지 않는다. 미정 제안은 확정된 의미 구조 밖에 보관하며 모든 채널에서 미정 표시를 유지한다.

사용 환경의 화면 크기는 dahaze 설정이다. 환경별 역할·허용 동작·경로 소속처럼 검증에 필요한 사실은 컴파일러 계약으로 전달한다. 별도 화면 ID로 표현 가능한 부분을 먼저 활용하고, 단순 해상도 차이에 문법을 추가하지 않는다.

레이아웃 렌더러는 IR의 의미 요소를 React 컴포넌트로 결정적으로 그린다. 표·카드 같은 같은 목록의 시각 표현은 dahaze에서 선택할 수 있다. 새로운 데이터 조작이나 동작 의미가 필요한 경우에만 문법 확장을 검토한다. AI가 임의의 실행 코드를 생성해 화면으로 띄우는 방식은 사용하지 않는다.

AI 작업은 프로젝트 작업으로 보관하고 진행·취소·재시도 상태를 제공한다. 장시간 생성은 요청 연결과 독립적으로 재개할 수 있게 설계한다. 첫 구현은 PostgreSQL 작업 기록과 별도 실행 프로세스를 후보로 하며, 기존 운영 환경을 확인해 실행 방식을 확정한다. 컴파일 SDK는 스레드로 넘기고 취소·재시도로 이중 적용되지 않게 한다.

서버 상태는 Query가, 저장 전 일시적 조작은 zustand가 소유한다. 의미 변경을 제출한 뒤에는 서버 초안 버전으로 관리한다. 적용은 서버에서 기준 프로젝트 버전과 source hash를 확인하고 원자적으로 수행한다.

## 6. 초안·적용·복원 계약

1. 인터뷰 대화와 제안은 자동 보관한다. 생성된 RSPDL 초안은 컴파일 결과와 함께 보관한다. 오류가 있어도 초안 보관은 가능하다.
2. 변경안에는 기준 프로젝트 버전, 관련 원문, 추가/수정/삭제, 결정 이유, 컴파일 결과와 검사 범위를 포함한다.
3. 검토 중 새 편집이 생겨 기준이 달라지면 적용하지 않고 최신 상태로 다시 작성·검증한다.
4. 사람의 적용은 명시적 저장이다. 여러 문서와 관련 메타데이터를 하나의 트랜잭션/변경 묶음으로 확정한다. 의미 오류가 남은 후보는 확정 상태로 승격하지 않는다.
5. 디자인 수치의 자동 저장은 별도 편집 이력으로 남긴다. 적용 시점의 디자인·샘플·환경·미정 상태도 프로젝트 스냅샷에 연결한다.
6. 복원은 과거 이력을 지우지 않고 해당 상태를 새 버전으로 만든다. 전달된 스냅샷은 변하지 않는다.
7. 컴파일러 버전·원문 hash·wire schema를 스냅샷에 기록한다. 옛 결과를 새 버전 검증으로 표시하지 않는다. 옛 버전 재컴파일이 필요하면 별도 프로세스에서 실행한다.

원문과 재생성 불가능한 상태만 권위 있는 저장 대상으로 둔다. IR을 모델/화면/정책 테이블로 정규화하지 않는다. 스냅샷에 포함된 컴파일 JSON도 원문에서 유래한 파생물로 취급한다. ADR-0003과 ADR-0005를 이 계약에 맞게 보완한다.

## 7. 컴파일러 확장이 필요한 부분

현재 YAML 흐름은 출발 화면·버튼·도착 화면·설명을 가진다. 설명은 조건식이 아니다. 기존 조건부 생산·이벤트·정책 분석을 재사용할 가능성이 있으므로 새 DSL부터 만들지 않는다.

| 순서 | 계약 | 검출할 사례 |
|---|---|---|
| C1 | 기능·행동·요소 식별과 원문 위치, 역할·사용 환경의 의미 연결 | 버튼의 행동/필드 연결 오류, 사용 환경에서 허용하지 않은 행동 |
| C2 | 업무 시작·완료, 입력/조회/계산/생성에 의한 데이터 확보, 단계 간 전달 | 필요한 연락처 확보 단계를 우회해 예약 완료에 도달 |
| C3 | typed 행동 결과와 경로/같은 화면 상태/메시지/팝업 처리 연결 | 명시된 실패 결과의 처리 누락, 취소 정책과 버튼 결과 충돌 |
| C4 | 데이터 상태·조건, 복구·재시도·타임아웃 의무의 제한된 의미 | 인증 조건 우회, 명시한 좌석 해제 의무 누락, 명시한 중복 방지 정책 위반 |

모든 화면 요소에 안정적 ID가 있는 것은 아니다. 직접 편집 후 배치 유지와 요소별 진단 연결을 위해 compiler-owned 식별 또는 편집 API를 먼저 설계한다. 배열 인덱스/소스 위치만으로 영구 매칭하지 않는다. 추정 대응이 모호하면 확인 대상으로 남긴다.

format SDK는 문자열 정규화 도구이며 의미 편집 API가 아니다. 원문 보존과 정확한 요소 교체를 위해 컴파일러의 구조화 편집 지원을 평가한다. dahaze에 별도 YAML 해석기를 만들지 않는다.

현재 TotalDecisionPoint/SMT 기반 분석은 존재하지만 화면 경로와 통합된 범용 조건 분석이라고 볼 수 없다. 닫힌 enum과 제한된 상태 전이부터 계약을 정한다. 반복 경로는 순환 횟수 나열만으로 안전하다고 판정하지 않고 유한 상태 분석/보수적 근사 등을 검토한다. 지원 밖 조건·timeout·solver UNKNOWN은 검증 완료로 바꾸지 않는다.

‘실패 처리가 필요하다’는 판단에도 명시적 결과 집합과 완료/복구 의무가 필요하다. 선언하지 않은 실제 업무 의무를 컴파일러가 추측하지 않는다. AI가 후보를 질문하고 사용자가 채택한 뒤 검사한다. 동시 결제/외부 시스템의 실제 정확성까지 정적 명세 검사로 보장한다고 주장하지 않는다.

## 8. 실행 단계와 선행 관계

| 단계 | 주요 작업 | 완료 증거 |
|---|---|---|
| 0. 계약과 기준 사례 | 최신 develop 기준 확보, 버전별 capability 대조, 공통 모델의 파일 간 참조 검사, 항공 예약 정상·실패 사례, C1~C4 RFC | 각 요구를 현재 가능/확장 필요/미지원으로 매핑하고 반례 기대 결과 고정 |
| 1. 프로젝트 작업 기반 | 지속 인터뷰·결정·미정·초안, 여러 문서 컴파일, 변경 묶음 적용·복원, 버전 경쟁 처리 | 새로고침 후 재개, 오류 초안 보관, 한 번 적용·전체 복원, 중간 실패 시 부분 저장 없음 |
| 2. 인터뷰와 검토 | 질문→작성→결과 반복, 명세+IA, 진단·질문·미정·미지원 구분, 영향순 해결·보류 | 핵심 정책을 결정하고 반례 진단에서 질문·수정·재검증·다음 문제로 진행 |
| 3. 편집 가능한 화면 | C1 연동, 사용 환경, 회색 렌더러, 샘플 묶음, 디자인 편집, 의미 편집→초안, 배치 보존 | 필드/버튼/경로 변경이 compiler gate를 통과하고 원문과 화면이 같은 버전 |
| 4. 경로 검증과 체험 | C2·C3 및 항공 사례에 필요한 제한된 C4, 입력·화면 이동, 상황 선택, 같은 화면 오류·팝업 | 예약 경로와 실패·재시도 체험, 입력 우회·실패 처리 누락 등 반례의 compiler 진단 |
| 5. 개발 전달 | 요소별 기능/정책/모델 탐색, 전체 프로젝트 스냅샷, 읽기 전용·다운로드·MCP, 버전 비교 | 모든 채널이 같은 version/hash를 참조하며 미정·진단·미지원도 동일하게 노출 |
| 6. 후속 확장 | 검증 가능한 조건·복구 범위 확대, 필요 시 정책 평가에 따른 자동 체험 | 추가 업무별 정상/실패/오탐 방지 사례와 지원 범위 공개 |

0단계 이후 dahaze 기반과 compiler 확장은 독립 개발할 수 있지만 3단계는 요소 식별·의미 편집 계약, 4단계는 경로 계약 완료에 의존한다. 각 단계는 검토 가능한 결과를 내되, 1~5단계 통합을 첫 제품 목표로 삼는다. 그래프만 구현하고 검증을 전부 후속으로 미루지 않는다. 고급 자동 정책 실행은 첫 목표에서 제외한다.

공수/기간은 지금 숫자로 확정하지 않는다. 가장 큰 변동 요인은 C2~C4의 의미 분석과 파일 간 공유 계약이다. 0단계에서 작은 반례를 실제 컴파일러로 통과시킨 뒤 compiler 작업과 dahaze 작업을 별도 산정한다.

## 9. 성능과 화면 구성

첫 화면은 검토 요약, 상세 탐색은 기능명세·데이터 모델·IA·화면 흐름으로 둔다. 선택한 대상의 관련 명세/진단과 AI 인터뷰를 연결한다. 사용자는 원문을 직접 쓰지 않아도 작업할 수 있고 필요할 때 원문 위치를 볼 수 있다.

30/60/100 화면과 2/4 사용 환경으로 측정한다. 그래프 전체 축소 상태는 가벼운 요약, 확대·선택 시 상세 와이어프레임을 렌더링한다. 실제 폼 실행은 체험 모드에서 활성화해 캔버스 이동과 입력이 충돌하지 않도록 한다. 환경·여정 필터는 탐색을 위한 것이며 부분 전달 기능이 아니다.

성능 목표는 대표 브라우저·기기에서 측정해 정한다. 초기 목표 후보는 100개 화면에서 pan/zoom p95 프레임 33ms 이하, 로컬 선택 반응 100ms 이하이며 네트워크·LLM 대기와 구분한다. 생성은 기능 범위/페이지별 진행을 보이고 취소·재개할 수 있다. [React Flow 성능 가이드](https://reactflow.dev/learn/advanced-use/performance)의 memoization, 선택적 구독, 큰 트리 접기를 참고한다.

## 10. 필수 검증 시나리오

1. 아이디어로 인터뷰 시작→핵심 규칙 결정→명세·IA 작성→컴파일 결과와 변경 요약→적용.
2. 연락처를 직접 입력하는 정상 경로, 회원정보에서 가져오는 정상 경로, 어느 쪽도 확보하지 않는 실패 경로를 구분한다.
3. PC 한 화면/모바일 여러 단계가 같은 예약 계약을 충족한다. 임의의 필수 입력 우회는 검출한다.
4. 결제 성공/실패를 선택해 체험한다. 같은 화면 재시도 처리도 정상으로 인정한다.
5. 역할에 맞지 않는 행동, 취소 결과 충돌, 명시된 실패/복구 처리 누락을 각각 독립 반례로 검출한다.
6. 입력칸 크기 변경은 RSPDL에 영향을 주지 않는다. 필드 삭제는 의미 변경으로 검증한다.
7. 사용자 배치와 편집값은 AI가 새 요소를 추가한 뒤 유지된다. 중복 요소/ID 변경/삭제 후 복구를 검사한다.
8. 오류 초안·미정 요소·보류 질문은 재접속 후 남고, 미정 동작은 실행되지 않는다.
9. 생성 중 취소·실패·재시도와 적용 요청 중복, 검토 중 다른 탭 수정, 변경 묶음 중간 저장 실패를 검증한다.
10. 변경 묶음 복원과 전달본 비교가 원문·디자인·환경·샘플 상태를 일관되게 다룬다.
11. 읽기 전용 화면·다운로드·MCP에서 동일 버전·권한을 적용한다. MCP는 application 유스케이스만 호출한다.
12. compiler 규칙마다 정상·실패·경계·오탐 방지 conformance를 둔다. 미지원/UNKNOWN을 정상으로 표시하지 않는다.

코드 변경 제출 시 ./scripts/check.sh, compiler conformance, 대표 프로젝트 재컴파일을 수행한다. 버전 승격 시 프롬프트·출력 문법·SDK 응답·배포 wheel도 함께 검증한다. 이번 작업은 계획과 소스 조사이므로 테스트나 런타임 성능 검증을 수행하지 않았다.

## 11. 구현 착수 시 산출물

- dahaze: 현행 화면 보드 RFC를 본 합의로 갱신. 저장·초안·적용·프로젝트 스냅샷 ADR, 기능별 이슈, API 계약 및 생성 클라이언트 갱신 계획.
- rspdl-core: 기존 문법을 기반으로 C1~C4의 작은 RFC와 반례부터 작성. 문법·IR·진단·편집 SDK·포매터·conformance를 함께 정의.
- 공통: 검증 능력 표, 항공 예약 기준 프로젝트, 데이터와 정책 출처 연결, 첫 제품 완료 체크리스트.

구현은 develop 기반 이슈·브랜치·PR 절차로 진행한다. 현 작업에서는 브랜치 전환·병합·코드 수정·이슈 생성·배포를 수행하지 않았다.
